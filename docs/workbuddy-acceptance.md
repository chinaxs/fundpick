## 本轮已经修复

| 问题 | 证据与影响 | 修复 |
| --- | --- | --- |

## 仍未通过的事项

### P1 / T14：公司行为未接入主账本

`app/services/portfolio.py` 仅聚合买卖流水，`transaction.py`、`trade_fee_math.py` 同样未读取 `FundPortfolioFlow`。再投/拆分/转换即使已记录，主工作台、已持仓标识、可卖份额及 FIFO 赎回批次仍与平台不一致；现金分红也未进入主收益。转换只记录单边事件，缺少同笔转入转出的关联和成本结转。

验收例：买入 500 份→1:2 拆分→卖出 800 份应按拆分后的真实批次处理；当前只修复核对页，主卖出流程仍会按原 500 份拒绝。必须完成统一的事件重放/分平台成本口径，再验证纠错、重试、删除、收益和 AI 数据一致性。

### P1 / T08：部分模式的取消与失败计数没有接入

`scripts/sync_funds.py` 中风险/净值有逐基金 `PROGRESS.checkpoint()`，档案 `sync_details` 和重仓 `sync_holdings` 循环仍缺少对应检查与失败上报；逐只失败仅写 debug 并继续，最终可能显示 success。`SyncJobService._reconcile` 遇到存活 PID 直接返回，API 重启后原 watcher 丢失，超时进程不会由恢复逻辑终止。定时去重问题本轮已修，以上仍待处理。

验收应覆盖每个采集模式的取消、全部失败/部分失败，以及 API 重启后的超时收敛，不能仅 mock 任务表状态。

### P1 / T12：备份可恢复性和持久化未完成

`docker-compose.yml` 只持久化 MySQL，API 的日志/备份未挂卷；容器替换会丢失。`backup_db.py` 用 `capture_output=True` 在内存积累整库 SQL，`restore_drill.py` 又一次读入和解压整份文件，大库可能内存耗尽。

演练固定使用 `${MYSQL_DB}_restore_check` 并先 DROP，同库并发演练会相互破坏；缺少执行唯一的临时库名和可靠 finally 清理。创建临时库失败会直接返回、不写演练结果，后台可能继续显示旧成功。空表会导致 `ok=False` 却只设置 warning；只检查四张表非空也无法证明用户交易、待确认申请和公司行为完整恢复。

需补流式备份、原子落盘、备份清单/恢复核对、独立演练库和持久卷，再在隔离库实做备份→恢复→逐表核对。本轮没有执行涉及 CREATE/DROP DATABASE 的演练脚本。

### P2 / T11：登录次数冒充活跃与回访

`repositories/engagement.py` 用 `AuthSession.created_at` 统计活跃；同一会话持续访问工作台不会新增记录，刷新 token 也不改创建日，忠实回访用户会漏计。留存实现使用 8–15 天前注册队列，页面口径写 7–14 天；SQL 用户名前缀里的 `_` 仍是 LIKE 通配符，可能误排真实账号。交易转化包含已作废记录，待入账的首次记账却不计入。

需明确按访问行为记录每日活跃与首次转化时间，统一留存窗口、作废/待入账计数和测试账号过滤。

### P2 / T15：抓取时间未等于原始行情时间

`MarketIndexService.cache_meta()` 返回的是 `_cache_written`，分时与日 K 的 `data_as_of` 也使用该时间，而非上游最后分时点/最后交易日。周末新抓到周五数据时，会显示“刚更新”。无缓存的日 K 请求失败会返回空 points，`degraded` 仍可能为 false。`market_status()` 在未知年份按星期推断交易中，也没有向用户暴露日历未知。

需分开响应时间、抓取时间、原始行情时间；无原始时间时明确未知，不能用抓取时间替代。验证周末、长假、过期缓存、上游首次失败和未知年度。
