## 判断

当前具备基金工具的小规模试用基础：官网已经有筛选、详情、关注和模拟买卖；后台具备基金查询、手动同步、内容发布、会员与员工管理、审计和系统信息。

下一阶段最值得投入的是**数据可信、故障可处理、用户问题可定位**。基础管理页面已有，持续运营能力尚不完整。建议先完成数据质量与同步任务闭环，再补会员支持与运营分析。

## 数据快照：全量数量不等于可用覆盖

以下为开发库当时的聚合结果，不代表线上数据或真实用户规模。

| 项目 | 数量 |

| 未删除基金 | 28,287 |
| 有最新单位净值 | 20,718 |
| 最新净值日期为 2026-11-06 | 19,434 |
| 最新净值日期为空 | 7,569 |
| 有近一年收益 | 18,491 |
| 有近一年最大回撤 / 夏普 | 各 15,047 |
| 有规模字段 | 13,825 |
| 已存历史净值序列的基金 | 9 |

1 月、3 月、6 月等区间有收益，但该库对应的回撤、夏普均未覆盖；风险采集目前主要填充 1 年、3 年、5 年。筛选器允许选中无风险指标的区间并排序，用户只能看到大量空值。

历史净值采用按需回填，因此“仅 9 只已有序列”本身不等于实现错误，但说明首访净值曲线、指定确认日查询依赖补采或手动确认。应优先给持仓与关注基金缓存数据，并显示待补齐状态。

缺失还可能来自新基金、产品类型或已停止更新，不能把所有空值判为采集失败。当前是周末，2026-11-06 为周五，也不应仅因相隔两天就判定数据异常。

## 优先修正的具体问题

### 1. 风险指标采过一次后缺少更新机制

`services/api/scripts/sync_funds.py:336` 的 `sync_risks` 以“存在任意非空夏普值”排除基金；没有按基准日或过期时间重新采集。`sync_snapshots` 又只更新收益和 `nav_date`，会形成收益日期更新、旧风险值继续保留的组合。

建议按基金、区间、数据所属日期分别记录与刷新收益/风险指标，补充来源及更新时间。后台覆盖率也应分成收益、回撤、夏普、净值序列，而非仅以“存在 1y 指标行”表示区间指标覆盖。

证据：`scripts/sync_funds.py:272`、`:336`；`app/repositories/admin_stats.py:71`。

### 2. 同步任务状态存在竞争，成功不代表数据完整

`SyncJobService.start` 先保存 running，再启动进程并写 PID；`_reconcile` 将没有结果且没有 PID 的任务判为 failed。隔离核对确认：一条刚创建、尚未得到 PID 的 running 任务会直接被改成 failed。启动窗口中被轮询就可能误判。

“查是否有 running，再插入任务”没有数据库级互斥，多 worker 并发触发可能同时通过。采集脚本会跳过单个分类/基金失败，主流程结束仍写 success；任务表没有目标数、成功数、失败数和失败代码。

采集页面还在异步加载任务之前检查是否需要轮询，重新进入已有运行任务的页面时可能不恢复 3 秒轮询。其每分钟定时器只更新汇总状态，不更新任务表。

建议补充 queued/starting/running/partial_success/success/failed/cancelled 状态、心跳与启动宽限时间、数据库互斥、结果计数及失败清单；先完善手动任务，再加入收盘后的日常调度。按业务交易日和产品类型判定新鲜度，并在日志/结果文件持久化上适配部署方式。

证据：`app/services/sync_job.py:92`、`:117`、`:165`；`scripts/sync_funds.py:276`、`:917`；`apps/admin/src/views/data/DataSyncView.vue:48`、`:116`。

### 3. 账号保护与权限仍有缺口

- 员工批量删除会跳过本人，但单条删除、编辑禁用和取消超管身份没有相同保护；最后一名有效超管也没有保护。需要服务端事务校验，避免管理入口被锁死。
- 门户会员页的菜单允许普通员工进入，而接口要求 SuperUser，界面与接口不一致。
- 会员批量删除把后台员工 ID 当成会员表的 exclude_id；两表独立，相同数字 ID 的会员会被错误跳过。
- 后台保存了 refresh token，但请求拦截器遇到 401 直接跳登录，没有使用续期接口。
- 改密或后台重设密码只更新密码哈希，旧 access/refresh token 没有会话版本校验；旧刷新令牌在其有效期内仍可续签。应补会话撤销、刷新轮换与登录限频。禁用账号已有服务端校验，应保留。

证据：`app/services/staff.py:48`、`:66`；`api/v1/admin/staff.py`；`api/v1/admin/users.py`；`apps/admin/src/router/index.ts:76`；`apps/admin/src/api/client.ts`；`app/services/auth.py`。

### 4. 上线配置与持续验证还没有闭环

生产配置当前仍接受占位 SECRET_KEY；隔离构造生产 Settings 已确认不会拒绝。Docker Compose 的 production 配置也保留占位值。应在生产启动时校验密钥与必需配置，并通过部署环境注入。

CI 已存在，但后端工作流没有配置测试数据库、迁移和基准数据，而多项集成测试依赖数据库及固定基金代码。需要独立测试库和可重复的测试数据。当前全量 `mypy app` 有 14 个错误，涉及 9 个文件，会阻断 CI 中的类型检查步骤；不能将“新增模块检查通过”视为全量检查已通过。

证据：`app/core/config.py:66`、`docker-compose.yml:43`、`.github/workflows/ci.yml`、`tests/conftest.py`。

## 当前最值得补的后台功能

**第一优先：数据质量中心。** 在现有基金页增加“缺净值、日期落后、缺风险、缺历史序列”等条件，按基金类型和适用区间统计；点击基金可查看字段来源、所属日期、最近采集结果和定向补采入口。以用户持仓/关注基金为优先级，避免每次全市场重采。验收标准是能从用户看到的一个空值定位原因，并完成补采验证。

**第二优先：可靠的采集任务中心。** 完成前述状态修正，展示目标/成功/失败/跳过数量、阶段与心跳，提供失败项重试、超时和取消；之后增加日常调度与失败告警。不是只展示进程退出码。

**第三优先：会员支持与模拟交易排查。** 提供会员基本状态、关注数、是否有持仓、最近操作及请求编号查询；对确需查看的交易明细增加权限和查看审计。按流水核对份额、成本、净值来源、费用及作废链条。初期以只读诊断和用户侧重新确认为主，涉及更正应有明确原因与留痕。

**第四优先：内容发布与账号恢复。** 文章编辑页补齐分类、来源名称/链接、预览与未保存提醒；门户补反馈与忘记密码流程。目前个人资料页提示邮箱可用于找回，关于页写“通过后台反馈”，但仓库没有对应用户可用闭环。

**第五优先：运营效果。** 仪表盘逐步增加活跃、首次关注、首次交易、7/30 日回访、异常反馈处理情况。指标定义需要过滤测试帐号并保护个人资产信息，先知道用户是否持续回来，再决定会员付费功能。

## 官网后续优化

1. 根据区间的实际可用性提示或限制风险排序，展示指标日期；基金 A/C 等份额区分清晰，避免收益排行被同一产品重复占据。
2. 增加最多 3 只基金的对比，重点比较费用、回撤、风险、区间表现和数据日期，帮助筛选后的下一步决策。
3. 持仓提供现有持仓导入、确认份额核对和历史导出；分红、转换、拆分要作为显式流水扩展，再完善现金流收益率。新用户不应被迫从第一笔历史买入重新手录。
4. 行情失败回退旧缓存时返回原数据时间、缓存年龄与降级状态。当前 quotes 每次把 as_of 设为当前时间，旧数据回退不带缓存年龄，界面容易误解为刚更新的行情。
5. 产品文案与现有能力一致：现有风险指标主要取自外部源，关于页对可复算口径的承诺需要对应数据来源和具体定义；面向访客的技术栈介绍、后台入口与 API 文档入口也可按产品定位收敛。

## 建议实施顺序与验证记录

先修风险刷新、任务状态竞争和账号保护等明确问题；下一轮功能以数据质量中心和采集任务中心为主；随后做会员支持、反馈和内容编辑闭环。精细角色、支付会员、大规模 AI 功能可在真实运营需求明确后继续投入。

本次验证：前端 workspace 类型检查通过；后端 Ruff 通过；全量 mypy 发现 14 个错误；只读事务取得数据覆盖与任务聚合；隔离核对复现生产配置接受占位密钥、启动期无 PID 任务被判失败。未触发采集或修改业务数据，也未进行真实员工删除/降权验证。
