# ADR-0017：公司行为按平台归属，写入串行化并提供幂等键

- 状态：已采纳
- 日期：2026-11-08
- 关联：[ADR-0016](0016-ledger-replay-as-source-of-truth.md)

## 背景

统一账本上线后，第二轮验收暴露三类问题：

1. **同一笔再投在两个平台各加一次**。旧实现按平台过滤流水后再重放，
   公司行为没有平台字段，于是"全基金再投 10 份"在 A、B 两个平台
   各算出 110 份可卖，合计比实际持仓多 10 份；
2. **转换复制份额**。转出 50 份、净值 2 元，转入 100 份、净值 1 元，
   保存后目标持仓只有 50 份——请求里的 `target_shares` 被静默忽略；
3. **并发转换超卖**。两个请求同时读余额再落库，都通过了校验。

## 决策

### 1. 公司行为必须归属一个平台

`fund_portfolio_flows` 增加 `platform`：

- 用户指定优先（持仓工具表单可填）；
- 未指定且只有一个持仓平台 → 自动补齐；
- 未指定且有多个平台 → **拒绝（422）并要求选择**。

"再投发生在 A 还是 B" 是我们查不到的外部事实。按"份额最大"猜一个虽然可复现，
却会改错平台余额、FIFO 批次和赎回费——可复现不等于真实，因此不再推定。
历史缺归属的记录保留 `platform=NULL`，不静默升级为真实归属；
重放时按固定规则落到某平台仅用于让总额自洽，界面仍显示"平台未知"。

### 2. 单平台结果是"投影"，不是"过滤后重算"

`replay()` 永远先重放**全部**平台的流水与公司行为，最后按 `platform`
挑出该平台的状态。这样"各平台份额之和 = 全基金份额"由结构保证，
不需要靠调用方记得过滤。

### 3. 转换两侧各存各的成交数据

`convert_out` 与 `convert_in` 分别保存 `shares_delta / nav / cash_amount`。
请求新增 `target_shares / target_nav / target_cash_amount`：
优先用用户填写的确认值，其次按"转入金额 ÷ 转入净值"推算，
最后才退回与转出份额相同，并在备注里写"按转出份额推定，请与回执核对"。
转出成本按移动平均结转（与卖出同口径），转入成本取结转金额。

### 4. 写入共用会员行锁 + 幂等键

`import_positions / add_flow / delete_flow` 与买卖共用
`SELECT users.id FOR UPDATE`，并在同一事务里用当前读（`FOR UPDATE`）
重放余额；`request_key`（唯一索引 `user_id + request_key`）保证网络重试
只记一笔；`request_hash` 保存请求内容摘要，同一个键换了金额/份额/日期返回 409，
不能静默沿用旧记录。删除改为软删（`deleted_at`），墓碑保留键与摘要，
旧请求重试返回"记录已删除"，不会把分红重新入账。

### 5. 写入前后都要验证整本账

新增公司行为时先 `flush`，再重放全部受影响基金（转换两侧都在内）：
出现负份额、批次不足或成本为负，整组回滚并返回 409——补录 D+1 的转换
不能让 D+3 已经成交的卖出变成负份额，也不能只写进转出侧。

删除（软删）前同样重放：删掉拆分会让后续卖出变负数时拒绝，要求先倒序撤销。
作废交易检查"这笔之后还有公司行为"。

### 6. 转换的"毛额/净额"分开记

`cash_amount` 是源侧转出的毛金额，`net_amount` 是目标侧实际到账的净额。
记账用净额与结转成本比较，差额（费用/损耗）进入已实现收益——
否则"转出 100、到账 90"里的 10 元会从收益里凭空消失。
净额缺失的老数据退回配对转入侧金额，再退回毛额。

### 7. 历史事件的费率只看当日

赎回费的 FIFO 批次重放必须 `until=卖出日`：之后录入的转换/再投不能吃掉
卖出日还存在的批次，否则历史手续费会随新录入的事件变化。

## 后果

- 多平台用户的再投/分红必须自己选平台；不选就报错，不再替用户猜；
- 写入路径多一次行锁，单用户串行化，换来不会超卖；
- 历史数据（`platform` 为空）仍可用：重放按固定规则落平台以保持总额自洽，
  但记录本身保留"平台未知"，不回填、不冒充真实归属；
- 删除变成"有依赖就拒绝"，用户需要倒序撤销，这是刻意的：悄悄删掉会直接
  把后续账本算成负数。
