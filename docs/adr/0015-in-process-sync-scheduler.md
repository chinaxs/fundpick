# ADR-0015：进程内轻量调度器负责采集定时

- 状态：已采纳
- 日期：2026-11-08

## 背景

采集一直靠人在后台点「立即同步」。真实运营里净值和风险指标是日频数据，
需要每天固定时间跑一次；没有定时，数据新鲜度完全取决于谁记得点按钮。

约束：

1. 目前是单机（或少量 worker）+ MySQL 部署，没有消息队列，也不想为
   "每天跑一次"引入 Celery/Redis；
2. 采集脚本本身是独立子进程，已经通过 `sync_jobs` + 结果文件解耦；
3. 多 worker 时不能让同一时刻触发两次。

## 决策

在 API 进程内跑一个 `asyncio` 循环（`services/sync_schedule.py`），
每分钟读一次 `sync_schedules` 表：

- 配置只表达"每周几的几点跑哪个模式"，不引入 cron 表达式；
- 判断"今天该跑"需要同时满足：星期匹配、已过计划时间、今天没跑过、未超 6 小时补跑窗口；
- 触发时复用 `SyncJobService.start`，因此**数据库互斥、运行中检查、审计、
  子进程、进度文件全部复用**，调度层不重复实现；
- 只有任务真的启动后才写 `last_run_on`，被"已有任务在运行"挡下时下一轮继续尝试。

调度器由 `SYNC_SCHEDULER_ENABLED` 控制，关闭后完全不影响手动触发。

## 备选方案

| 方案 | 为什么没选 |
| --- | --- |
| 系统 cron / launchd 调 CLI | 需要额外部署与日志轮转，且"谁在跑、跑到哪"回到文件里，后台看不到 |
| Celery + Redis | 为一天一次的任务引入 broker、worker、结果后端，运维成本远大于收益 |
| APScheduler 进程内 | 功能更全但多一套依赖与状态存储；我们的规则简单到一张表就够 |

## 后果

- 单实例部署完全够用；多实例时每个进程都会检查，但数据库互斥保证只有一个任务启动，
  且 `last_run_on` 由成功启动者写入，不会有重复任务；
- 如果将来需要"分钟级/依赖式"调度，应换成外部调度器，本模块整体删除即可，
  不影响任务表与脚本；
- 已知限制：进程停机期间错过的任务最多补跑 6 小时，超过就跳过——
  这是刻意的，避免长时间停机后开机立刻跑一轮全量把机器压住。
