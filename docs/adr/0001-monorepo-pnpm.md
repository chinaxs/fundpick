# 0001 · 用 pnpm workspace 组织单仓多包

- **状态**：已采纳
- **日期**：2026-11-05

## 背景

项目包含后台管理、门户网站、后端服务三个可独立部署的单元，其中两个前端共享类型定义、常量与工具函数。
如果拆成多个仓库，共享代码需要发包或复制粘贴，接口改动时容易出现"前端类型没跟上"的问题。

## 决策

采用 **pnpm workspace** 单仓多包：`apps/*` 放应用，`packages/*` 放共享包，`services/*` 放非 JS 服务（Python）。
共享包通过 `workspace:*` 协议引用，构建产物 `dist/` 参与编译。

## 理由

1. 一次提交可同时改后端 schema、共享类型、两个前端，避免跨仓库版本对齐成本。
2. pnpm 的严格 node_modules 结构能暴露幽灵依赖，天然适合 monorepo。
3. `workspace:*` 让依赖关系显式化，构建顺序由 pnpm 自动拓扑排序。

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 多仓库 + 私有 npm 包 | 每次改动要发包、升版本，小团队负担过重 |
| npm/yarn workspaces | pnpm 在磁盘占用与依赖隔离上更好，且团队已装 |
| 单仓但共享代码用相对路径 import（不建包） | 路径会变成 `../../../packages/...`，无法约束边界 |

## 后果

- 好处：改动原子化、类型天然同步、CI 可只跑受影响包。
- 代价：仓库体积变大；CI 需要缓存 pnpm store；新人需理解 workspace 概念。
- 重新评估触发条件：团队规模超过 30 人或构建时间超过 15 分钟时，考虑拆库或引入 Turborepo/Nx。
